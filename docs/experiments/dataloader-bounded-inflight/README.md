## 原因与最小修改

旧实现提交整个Epoch；结果队列满后，消费者可把后续结果搬进pending，为Worker
腾出空间，因此结果队列有界不限制全局未交付任务。慢首Batch期间可积累整个Epoch。

新实现只提交初始窗口W，每顺序取出一个Batch归还一个名额，再补交至多一个。
因此排队、Worker处理中、结果队列和pending合计未交付任务≤W；pending插入瞬间
至多W个，交付后至多W−1个。消费者当前已取出的Batch不计入该预取窗口。

保留原有顺序、显式indices、重复样本、shuffle种子、末批、Epoch重置及close接口。
关闭时向任务队列发唤醒标记，使等待下一任务的Worker能够退出；沿用已有停止Event、
结果队列排空与真实join。没有新增调度层、线程池或无界模式。

异步prefetch_factor=0/负值现在明确报错；0不再表示Queue的隐式无界容量。
默认正值2不变，同步num_workers=0不受此异步参数影响。
Batch预算不是固定字节配额：Worker临时样本/组装副本、调用方保存的已交付数据、
分配器与索引数组仍占内存，详见源码分析，不能把W直接当作进程RSS上限。

## 测量协议

所有比例来自本轮匹配实验，不使用上一阶段成绩。固定seed42随机化每轮配置顺序，
各配置3次独立进程；最多4 Worker，正式测量不包裹Queue或pending。

- **real-fast**：原4H相同1024张真实图像，Batch4，open_stream=True，快速逐批消费。
- **real-consumer**：相同图像及Batch，每次消费后固定sleep4ms，模拟较慢消费者。
- **straggler**：512个合成样本，形状同真实图像；首样本sleep1秒，每样本额外sleep0.5ms。

后两种控制负载不是实际训练或GPU实验。完整墙钟包含迭代启动、全部消费及清理；
RSS是每个子进程的生命周期高水位，包含解释器和库。文件缓存不清理，不能称为冷盘基准。
所有预处理沿用上一阶段，不将已有异步/文件句柄收益计作本轮新增收益。

## 默认2 Worker、prefetch=2的结果

每项为3次独立进程的均值±样本标准差；吞吐单位samples/s，真实输入时即images/s。

| 负载 | 原吞吐 | Bounded吞吐 | 吞吐变化 | 原峰值RSS MiB | Bounded峰值RSS MiB |
|---|---:|---:|---:|---:|---:|
| 真实图像快速消费 | 2073.73±48.51 | 2104.76±59.86 | +1.50% | 229.95±1.03 | 230.01±0.75 |
| 真实图像4ms消费者 | 966.35±2.76 | 966.06±2.30 | −0.03% | 233.49±0.65 | 232.20±0.74 |
| 合成慢首Batch | 499.50±0.86 | 440.79±1.78 | **−11.75%** | **291.34±0.92** | **215.59±0.24** |

正常真实图像未出现大规模pending积压，RSS基本不变；+1.50%的平均吞吐与波动重叠，
不宣称稳定加速。慢消费者整体吞吐基本不变。

慢首Batch时平均峰值RSS降低75.75MiB（约26.0%），但是每轮墙钟从1.02502秒增至
1.16156秒。独立诊断pending插入峰值从128降至4，数组载荷从77.34570降至2.41705MiB，
降低96.875%。**pending载荷是单次插桩计数，不等于三重复RSS或进程总内存。**

## 吞吐退化与等待时间

| Worker / prefetch | 真实快速吞吐变化 | 4ms消费者吞吐变化 | 慢首Batch吞吐变化 |
|---|---:|---:|---:|
| 2 / 1 | −3.10% | −0.17% | −12.26% |
| 2 / 2 | +1.50% | −0.03% | −11.75% |
| 2 / 4 | −0.93% | −0.09% | −11.30% |
| 4 / 1 | +2.02% | +0.62% | −5.98% |
| 4 / 2 | +1.08% | +0.05% | −5.57% |
| 4 / 4 | **−5.36%** | −0.17% | −5.30% |

全部负结果保留。真实快速4/4约−5.36%，不能把所有正常配置称为无性能成本；
共享服务器三重复的波动也保留，没有删除较慢轮次或继续调整至出现正值。

慢首Batch的取舍有直接流程证据：旧实现可在首Batch等待期间让另一Worker预先完成
整个Epoch；新实现完成窗口内任务后必须等待消费者归还名额。默认2/2独立诊断：

| 累计Queue操作墙钟，ms | 原实现 | Bounded |
|---|---:|---:|
| 慢首Batch result.get | 1005.12 | 1151.48 |
| 慢首Batch index.get | 1.24 | 999.42 |
| 真实快速 result.get | 438.74 | 427.72 |
| 4ms消费者 result.put | 1241.26 | 3.11 |
| 4ms消费者 index.get | 1.91 | 1287.99 |

index.get增长表示Worker等待新的提交名额，是有界背压的预期结果；消费者已是瓶颈时，
等待增加未使端到端模拟吞吐显著下降。该负载的背压从result.put转移到index.get，
并非节省了约1.2秒CPU计算。队列计时包含锁/调度，跨Worker会重叠，
不能当作CPU计算时间相加。上述单次诊断与正式三重复吞吐严格分开。

## Epoch长度与边界验证

相同2 Worker/prefetch2的慢首Batch，Epoch为32/128/256个Batch时：

| Batch数 | 原峰值RSS MiB | Bounded峰值RSS MiB | 重复范围 |
|---:|---:|---:|---|
| 32 | 232.60 | 216.29 | 单次长度观察 |
| 128 | 291.34 | 215.59 | 正式三重复均值 |
| 256 | 369.16 | 216.39 | 单次长度观察 |

这些数据支持未交付载荷不再随Epoch积累，两个端点不是三重复基准。
18种Bounded诊断配置中，提交窗口均满足W约束，另18种基线配置保留作对照；真实数据旧实现提交峰值256，新实现按配置
限制为2/4/8/16。已提交任务数量不是已分配图像数量，因此不能仅凭256任务推断256份
图像同时驻留，内存结论以上述实际pending和RSS为准。

## 验收结论与待审查项

有界调度达成目标，并保留顺序和生命周期语义。它主要改善慢Batch下的内存上界，
不是一项普遍吞吐加速。保留默认prefetch=2；没有增加无界兼容开关或自动调优。
若未来重尾读取场景占比较高，应按有限内存预算评估窗口和负载波动，而非无限缓存。
本轮未测GPU训练，不把CPU结果写成训练加速，也不自动推进其他功能。
